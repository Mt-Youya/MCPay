# MCPay PPT 制作提纲

本提纲建议做成 8 页、4–6 分钟的项目介绍。每页只传达一个判断，避免把代码结构堆到投影上。

## Slide 1 — 标题：让 Agent 可以购买服务

- 标题：**MCPay — Agent Commerce on Monad**
- 副标题：目标 + 预算 → 自主发现、支付、执行
- 画面：一条从任务卡片到研究结果的单线流程
- 讲述：Agent 已会用工具，但很少能在运行时与陌生服务建立付费关系。

## Slide 2 — 问题：工具调用不等于商业能力

用四个问题排版：

1. Agent 需要什么服务？
2. 多个 Provider 时选谁？
3. 没有预先 API Key 时如何支付？
4. Provider 如何只为已付款的 Agent 执行一次？

落点：MCPay 解决的是完整商业闭环，不是再加一个工具目录。

## Slide 3 — 产品体验：用户只给目标与预算

展示 Web 截图或线框：

```text
Research the Monad ecosystem …
Budget: 0.01 MON
[ Run Agent ]
```

讲述：预算是用户授权边界；用户不需要逐笔点确认。

## Slide 4 — 核心流程：从 402 到付费执行

直接使用 [`SYSTEM-ARCHITECTURE.md`](SYSTEM-ARCHITECTURE.md) 的时序图，并高亮三步：

```text
Provider 402 → Monad 转账 → Provider 验证并执行
```

讲述：支付条款来自 Provider；Agent 不会向任意地址、任意金额付款。

## Slide 5 — 为什么 Agent 的选择可信

- LLM：理解目标，只能选择受支持的 `web-research`。
- 确定性规则：按声誉 50%、质量 30%、价格 15%、延迟 5% 排序。
- 预算校验：超预算不付款。

一句话：**把语义判断交给模型，把经济决策留给可测试规则。**

## Slide 6 — 为什么 Provider 可以信任付款

展示“支付证明一次性兑换”的小图：

```text
交易哈希 → Monad 回执校验 → D1 原子写入 → 仅一次研究执行
```

讲述：验证成功、收款地址、精确金额和未被消费缺一不可；重复使用同一交易哈希得到 `409`。

## Slide 7 — 真实服务而非模型幻觉

- Tavily：实时检索最多 5 条证据。
- DeepSeek：只基于证据做流式综合。
- 返回：研究正文 + 标题/URL 引用。

画面：一边是流式正文，一边是来源链接；不要展示 API Key 或完整提示词。

## Slide 8 — 当前成果与下一步

| 已完成 | 下一步 |
| --- | --- |
| 402、Monad Testnet、D1 防重放、流式研究、引用 | 多 Provider、智能账户限额、信誉、退款/争议 |

收束句：

> MCPay 让 Agent 不止会调用工具，而是能在预算约束下参与可验证的服务经济。

## 现场演示顺序

1. 先展示 `demo` 模式，确认 UI、Offer 排名和预算不足分支。
2. 切换 `live` 前确认 Provider 健康检查、Agent Wallet 余额、Tavily/DeepSeek 密钥与 Turnstile。
3. 运行一笔小额 `0.01 MON` 任务；展示 402、交易哈希、流式正文和引用。
4. 不在演示中暴露私钥、API Key、Cloudflare Secret、完整收款地址以外的敏感配置。

## 评委问题的安全回答

- **为什么用链？** 在陌生 Agent 与 Provider 间，链提供可独立验证的结算证明。
- **为什么不是 Stripe？** Stripe 面向预先建立的商户关系；这里重点是运行时的机器对机器发现与结算。
- **如何避免乱花钱？** 当前实现通过任务预算和确定性排序限制；智能账户策略是下一步。
- **是否生产可用？** 核心闭环已落地在 Testnet；托管、争议处理、多 Provider 与更强的账户策略仍未完成。
