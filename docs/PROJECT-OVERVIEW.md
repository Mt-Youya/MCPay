# MCPay 项目全景

本页是面向项目介绍、答辩与 PPT 的事实基线。除非现场演示已经验证，请不要把“已接入”的能力表述成“已在主网大规模运行”。

## 1. 要解决的问题

现有 AI Agent 可以推理和调用预先授权的工具，但通常无法在运行时建立新的商业关系：它不知道该买什么、如何比较陌生 Provider、怎么付款，以及付款后如何证明自己有权执行服务。

MCPay 将这个缺口定义为 **Agent Commerce**：在用户授予的预算边界内，Agent 代表用户完成“发现 → 评估 → 支付 → 执行 → 返回可核验结果”。

## 2. 产品输入与输出

| 输入 | MCPay 的动作 | 输出 |
| --- | --- | --- |
| 任务目标 | LLM 将目标映射到受支持的 `web-research` 服务 | 规划说明 |
| MON 预算 | 对 Offer 做确定性排序并校验可负担性 | 选中的 Provider 或预算不足结果 |
| 可支付 Offer | 向 Provider 请求执行，接收 `402` 支付条款 | 收款地址、MON 原子单位、网络 |
| Agent Wallet | 发送 Monad Testnet 原生 MON 转账 | 交易哈希 |
| 交易证明 | Provider 链上核验并消费该证明 | 一次研究执行与来源引用 |

## 3. 已实现的关键机制

### 预算是授权边界

用户不需要逐笔确认。编排层比较 `budgetMon` 与 Provider 返回且已交叉核对的 `amountMon`；价格超预算时不会发起支付，结果明确显示 `budget-exceeded`。

### 选择不是 LLM 随机决定

`packages/commerce` 对同一服务的 Offer 按以下权重排序：

```text
score = 声誉 × 0.50 + 质量 × 0.30 + 价格得分 × 0.15 + 延迟得分 × 0.05
```

LLM 负责解释“为什么需要 web-research”，而不是决定花多少钱。这使经济决策可预测、可测试、可在 PPT 中清晰解释。

### 402 是服务协议的一部分

第一次 `POST /execute` 没有支付证明时，Provider 返回 `402` 和机器可读的付款条款。Agent 付款后在第二次请求携带交易哈希、收款地址、支付原子单位；Provider 会校验这些条款是否与 Offer 一致。

### 支付证明只消费一次

Provider 读取 Monad 交易回执和交易内容，要求交易成功、收款地址正确、金额精确匹配。随后以交易哈希写入 Cloudflare D1；唯一主键与 `INSERT OR IGNORE` 使同一哈希不能再次兑换执行。

### 研究结果有证据边界

Provider 先用 Tavily 检索最多 5 条网页证据，再把“目标 + 证据”交给 DeepSeek；提示词约束模型只根据给定证据回答，并把每条证据的标题与 URL 作为引用返回。

## 4. 运行模式

| 模式 | 用途 | 外部调用 | 支付 |
| --- | --- | --- | --- |
| `demo`（默认） | 本地开发、UI 演示、回归测试 | 无 | 无；返回确定性模拟结果 |
| `live` | 真实展示完整商业闭环 | DeepSeek、Tavily、Provider、Monad RPC | Agent Wallet 在 Monad Testnet 真实转账 |

## 5. 可展示与不可夸大的边界

可以展示：任务预算、Offer 比较、402 往返、交易哈希验证、D1 防重放、实时证据、DeepSeek 流式综合、引用列表。

不要声称：生产级托管、多链支持、智能账户策略、链上声誉、托管/退款/争议处理、开放式服务市场、多个真实 Provider。这些仍是明确的后续方向。

## 6. 演示的一句话

> MCPay 让 Agent 带着明确预算，在运行时选择并购买陌生 Provider 的服务；支付不是结账页面，而是执行协议中的一个可验证步骤。
