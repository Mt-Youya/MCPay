各位老师好，我做的项目叫 MCPay。

我一开始想解决的事其实很具体：现在的 Agent 会调工具，但工具大多是人提前配好的。真到了运行时，Agent 想临时找一个服务、比较价格、付一笔小钱，再拿到结果，这套事还不太顺。

MCPay 就是把这段补上。用户只填任务和预算，后面的选择、付款和执行，Agent 自己走完。

---

这一页是我们碰到的几个实际问题。

比如，Agent 怎么知道该买什么服务？两个 Provider 摆在面前，选哪个？没配 API Key，钱怎么付？还有，Provider 收到一笔付款后，怎么避免同一笔钱被反复拿来兑换服务？

这些问题单看都不大，连起来就是一条完整链路。MCPay 做的就是这条链路。

---

用户侧其实很简单。拿这里的例子说，用户让 Agent 研究 Monad 生态，预算是 0.01 MON。

模型负责理解这个任务需要网页研究服务。但价格和选择不让模型拍脑袋决定。我们用固定规则排 Offer：声誉、质量、价格、延迟各有权重。超过预算，流程直接停，不会去付款。

所以预算在这里不是展示用的数字，它就是 Agent 能花多少钱的边界。

---

接下来是支付。

Agent 第一次请求 Provider 执行服务时，Provider 会回一个 402。这里的 402 不代表报错，它的意思是：这项服务要收费，价格、收款地址和网络都在这里。

Agent 先核对这份付款条款，再去 Monad Testnet 转对应金额。拿到交易哈希后，它带着这笔支付证明重新请求 Provider，Provider 才开始执行。

---

架构上，我们把事情拆开了。

主 Worker 负责接任务、规划、拿 Offer 和付款。Research Provider 负责报价、返回 402、验链上交易，然后做研究。Monad 负责提供交易回执，D1 负责记住哪笔交易已经用过，Tavily 和 DeepSeek 负责最后的研究结果。

这样做的原因很朴素：付钱和确认服务有没有资格执行，最好不要只靠客户端说一句“我已经付了”。

---

这里是防重放。

Provider 会自己去查 Monad 的交易回执：交易有没有成功，钱是不是到了指定地址，金额对不对。都对上以后，再把交易哈希写进 D1。

D1 这里用了原子写入。同一个交易哈希第一次可以兑换研究服务，第二次就返回 409。也就是说，一笔付款只对应一次执行。

---

研究部分也有一个边界。

Provider 先通过 Tavily 找网页证据，最多五条。DeepSeek 拿到的是任务和这些证据，再做流式整理。最后返回研究正文，同时把标题和 URL 一起带回来。

所以它不是让模型凭已有知识直接编一个答案。演示里也不会出现 API Key、私钥或者 Token。

---

最后说一下范围。

现在已经跑通的是：402 支付、Monad Testnet 转账、D1 防重放，还有带引用的研究服务。

但我们也没有把它说成生产级平台。多 Provider、智能账户限额、信誉、退款和争议处理，都还没做完。

这个项目目前证明了一件事：Agent 可以在用户给定的预算内，和一个陌生 Provider 完成一次可验证的服务交易。
